# Target-only missing client RPCs

`20261005_missing_client_rpcs.sql` adds three contracts absent from the private source metadata reviewed on 2026-10-05. These are new target functions, not functions exported from Supabase. The patch reads no source data, creates no tables or users, changes no existing rows, and changes no table grants or RLS policies. An existing function name/signature causes the transaction to fail instead of silently replacing an unknown implementation.

| Contract | Client expectation | Implemented behavior |
| --- | --- | --- |
| `dm_conversations()` | Eight named fields in `dm_list_screen.dart` | One last message per partner, deterministic equal-time ordering, incoming unread count over full history, latest-first list |
| `create_group(p_name text, p_member_ids uuid[])` | Scalar UUID in `group_provider.dart` | Atomic group/members, trimmed nonempty name, caller included, duplicate members removed, at least one other member |
| `check_in_venue(p_venue_id uuid)` | One `{venue_id, expires_at}` row in `venue_provider.dart` | Caller-only replacement including expired rows, four-hour server expiry, per-caller profile lock, ordered old/new venue locks, demo/missing venue rejection |

All functions require verified transaction claims with `role=authenticated`, an active profile, and no caller-supplied user ID. Conversations exclude banned/blocked partners. Group creation refuses missing/banned members and block relationships among selected participants. Both mutation RPCs require READ COMMITTED isolation and reject repeatable-read/serializable before writing, preventing stale transaction snapshots from bypassing checks after lock waits. These guards inspect server tables, including reverse blocks hidden by the ordinary API policy. Claims helpers do not authenticate requests; the chosen Auth issuer/PostgREST must verify signatures before setting claims.

Apply only after the authoritative target restore and ownership review. The patch requires an explicit session marker `nightowl.target_rpc_patch=approved-independent-target`, a reviewed nonsuperuser owner with no bypass-RLS/create-role/replication rights, ownership of all seven referenced tables, enabled nonforced RLS, expected column types, access to `auth.uid()`/`auth.role()`, and no API membership in that owner role. The functions use `SECURITY DEFINER` to access expired check-ins and reverse blocks, a fixed empty search path, qualified relations, explicit participant checks, and authenticated-only EXECUTE. API table privileges are preserved. Do not casually change forced RLS or transfer table ownership to pass this gate; resolve ownership/security choices deliberately before applying.

With a private independently verified target connection, run the patch as that reviewed owner. The nonsecret session marker can be supplied through `PGOPTIONS='-c nightowl.target_rpc_patch=approved-independent-target'`. Retain `ON_ERROR_STOP`, inspect the transaction result, then test the resulting named RPC parameters and JSON responses over the target API. The patch sends PostgREST a schema-cache notification only after successful commit. It has not been applied to managed Supabase or the reserved migration staging database.

## Limits that keep the release gate closed

The source's direct-table rules still need independent review. Its `group_members` SELECT policy is unrestricted and its INSERT policy permits a caller to join a known group ID; ban/block restrictions are absent from several direct message/check-in/group policies. This patch does not make those paths safe. The Dart group fallback now performs direct inserts only in managed mode when the server explicitly reports that the named RPC is missing; independent mode and RPC permission/validation/response errors do not use that fallback. Another client can still call directly granted table endpoints, so target policies must close those authorization gaps before release. Participant consent and future member additions/leaving are separate contracts; this patch implements the current group-creation selection semantics only.

Group creation acquires a SHARE lock on `public.blocks` before any profile locks. Normal block mutations acquire ROW EXCLUSIVE first, so a pending block completes before the group checks its fresh committed view, or a group completes before a later block begins writing. Parallel group creation retains compatible SHARE locks. This briefly delays block writes across the table and relies on short transactions. Broader operator/service transactions that lock profiles first and then mutate blocks can introduce reversed lock order and deadlocks; they must follow the reviewed order, use bounded transactions and handle transaction retries. A later block does not remove members from an already committed group; future contact enforcement still belongs to the target table/service ACL review.

Existing triggers, functions, foreign keys, defaults, counters and indexes must be restored and reviewed separately. The source check-in count definer function has no explicit search path, but its counter updates already qualify `public.venues`. The fictional fixture preserves that exact relevant body/path behavior; actual check-in/counter tests pass while inheriting the RPC's empty path. This does not certify the function's independent invocation or other restored definer functions. Profile-ban/block checks use the transaction's database view; later changes must also be enforced on future message/member operations. No complete auth/storage/realtime integration, signed-token validation or source-data reconciliation is claimed.

## Local verification

`backend/tests/run_rpc_patch.sh` accepts only a disposable database whose name ends in `_rpc_backend_test`. It builds fictional schema/rows from reviewed column and RLS shapes, uses a separate nonlogin nonsuperuser fixture owner, applies the patch under that owner, verifies runtime/permission behavior, and runs simultaneous check-in transactions. A superuser setup connection is needed for the isolated fixture; its password is supplied through a private `PGPASSFILE`, never an argument. The fixture is intentionally unrelated to source users/messages and is not an Auth implementation.

Tests cover complete unread counts beyond the old 400-row fallback, equal-time ordering, unrelated-user privacy, missing/malformed claims, bans and both block directions, selected-member block relationships, invalid group inputs, rollback after an actual member-insert trigger failure, expired/current check-in replacement, preserved other-user state/counters, unchanged table ACL/RLS, restrictive EXECUTE and migration ownership/marker/forced-RLS gates. Same-user transactions verify that a later check-in waits on the profile lock and leaves exactly one current venue. Opposite-user venue swaps use an additional fictional after-delete pause trigger to force counter-lock overlap; both transactions finish and counters remain consistent. Separate held transactions verify both group-first and block-first orderings using ordinary authorized block inserts. Unsupported snapshot isolation is rejected with no mutation.

The disposable database can be removed after inspection. Do not run these fixtures on the empty reserved migration target, a restored staging database or production. SQL claim fixtures exercise authorization/transactions; they do not replace real signed JWT and HTTP integration tests.

The complete suite passed against local PostgreSQL 17.11 on 2026-10-05 in about 4.4 seconds. Independent read-only review found no further actionable SQL defect in the tested ordinary API path. Managed Supabase and the reserved migration staging database were not modified.
